# 移動中の描画とフレーム間隔

低設定の30FPS制限を撤去し、両画質とも画面の更新タイミングで移動・描画する。低設定は影・反射・環境アニメーション・解像度で負荷を減らし、建物・地図・経路は維持する。

通常画質の影はVSMからPCFへ変更し、影のぼかし用の追加パスと受光面の余分な描画を削減。文字の蛍光看板は維持する。水面反射は画面と異なる出力形式のシェーダーを使うため、こちらも操作開始前に`compileAsync`で準備する。初めて水面が視野に入った時の同期コンパイルによる停止を防ぐ。

拡大・縮小や停止などによる描画要求は次の画面更新へまとめる。移動の更新が予定されていれば、その更新で一度だけ描く。HTMLラベルの配置では画面寸法を先に読み、ラベルごとの書き込みと寸法の読み直しを繰り返さない。

## 再現と比較

`npm run build`後、`out`をlocalhost:3001で配信し、Playwright CLIで`tests/browser/world-frame-rate.js`を実行する。日付のみ固定し、ネイティブのrAFと`performance.now()`を使う。`renderer.render`のうちメイン画面への描画だけをFPSに数え、反射パスは別に処理時間を記録する。コールバックが呼ばれただけのフレームを描画として数えない。

位置`(0,20)`から温泉へ歩き、1秒の助走後の5秒間を測る。各条件は新しいブラウザコンテキストで開始し、昼・夜をそれぞれ検証。PCは1440×900・DPR 2、スマホ幅は390×844・DPR 3・CPU 4倍低速化。Chromium／Apple M4の開発環境であり、スマホ実機やSafariの実測値ではない。

| 条件 | 変更前FPS | 変更後FPS | 最大描画間隔：前 → 後 |
| --- | --- | --- | --- |
| PC・通常画質 | 58.97 | 59.78〜60.01 | 116.6〜125.5ms → 34.0〜34.3ms |
| PC・低設定 | 30.00 | 60.00〜60.01 | 34.8〜34.9ms → 18.7〜21.8ms |
| スマホ幅・通常画質 | 59.90〜59.91 | 60.01〜60.08 | 38.9〜39.3ms → 30.3〜30.9ms |
| スマホ幅・低設定 | 29.99〜30.00 | 59.99〜60.00 | 35.7〜36.0ms → 19.3〜19.5ms |

変更後のp95間隔は通常画質19.5〜25.7ms、低設定18.0〜18.6ms。全8条件で55FPS以上、p95 30ms以下、最大65ms以下の検証基準を通過。PCの主描画のdraw callは約1,214〜1,222から1,058〜1,066へ約13%減少。反射の初回パスは改善途中に104〜119msの停止を再現し、準備を追加した後は最大約16msになった。

結果はローカルの`output/playwright/fps-before-native.txt`と`fps-final-native.txt`。`world-frame-input.js`では、同じ画面更新内の重複描画を変更前の最大3回から変更後の1回へ削減したことも確認。`world-frame-focus.js`は約0.7秒のツアー移動をPC／スマホ幅・両画質・4館の16条件で測り、58.9〜60.5FPS、最大間隔39.6ms。結果は`fps-input-after.txt`と`fps-focus-final.txt`。

## 回帰確認

単体テスト95件・型チェック・本番ビルドが成功。低設定のフレーム制限、同一画面更新内の重複描画、反射シェーダーの事前準備は修正前の失敗を確認してから修正した。

`world-ux.js`で5画面サイズのドラッグ・拡大・縮小・ピンチ・キーボード・停止、`world-halls.js`でツアー・途中離脱・戻る／進む・直接URL・低設定での同一形状、`world-ux-loading.js`で準備中の本文閲覧・画質選択・WebGL喪失・人物取得失敗、`onsen.js`で移動・屋根・低設定の同一形状、`security.js`で10ページのCSP・BGM・画質変更・自転車を確認。結果は`output/playwright/fps-regression-*.txt`。遅延した描画後のラベル位置を使ってホイール操作の対象を選ぶよう、操作テストも画面更新を待つ。
