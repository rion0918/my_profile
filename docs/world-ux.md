# 3Dワールドの操作性調整（2026-10-24）

採用担当者が案内から経歴・作品を読みたい場合と、PC・スマートフォンで自由に街歩きしたい場合を対象に調整した。3Dの操作に慣れていない人も、通常表示へすぐ進めることを前提とする。

スマホの一本指操作は、その後の[フリック移動](world-touch.md)で人物の移動へ変更。見渡しは二本指、マウスは従来どおりドラッグで操作する。HUDの常設項目は[HUDの整理](world-hud.md)を参照。

## 改善と確認基準

| 対象 | 変更・維持した動作 | 確認方法 |
| --- | --- | --- |
| 視野 | 初期表示は画面の縦横比に応じて最低12.4mの横幅を確保。人物を少し下に置き、進行先と建物を見渡す | `world-view.test.mjs`、`browser/world-ux.js`、各館の実画面 |
| カメラ | 縦ドラッグの逆転を修正。マウス・指と同じ方向に景色が動く。拡大・縮小・人物への復帰を追加 | 射影座標でドラッグ量を照合。ホイール・ピンチ・ボタン・＋／−／0、全体表示でもズーム方向が一致 |
| 移動 | 通常歩行2.775→3.2m/s、ダッシュ4.6→5m/s。歩行の姿勢は維持。浅瀬は1.1m/sを維持 | 歩行・アニメーション・壁や海岸の単体テスト、実ブラウザの移動距離 |
| 停止 | タップ移動と自転車を画面上の「停止」でも止める。Escape・フォーカス離脱・本文表示時の停止も維持 | 自動移動の途中停止と位置の不変性、入館・ツアー検証 |
| 小さい画面 | 操作ボタンは44px以上。折り返しに合わせてカメラ操作を配置し、現地の入館ボタンとも重ならないよう表示を調整。320px幅では名前と上部操作も別の行にする | 1440×900、390×844、375×667、320×568、844×390で座標・重なり・横溢れを検査 |
| 読み込み | 道路の結合計算をビルド時へ移動。モデル生成は途中でブラウザへ処理を返す。中断時は部分生成分も解放 | 読み込み途中の本文閲覧・画質切り替え、生成中のWebGL喪失、人物モデル取得失敗を再現 |
| 失敗時 | 入口カードでエラー案内が隠れない。通常表示と案内から本文へ進める | `browser/world-ux-loading.js`で実際に通常表示まで遷移 |
| 読みやすさ・支援技術 | 自転車ボタンのコントラストを改善。表示文言を含む読み上げ名へ揃える。キーボード操作と本文のフォーカスを維持 | axeとLighthouse、ツアーのTab／Shift+Tab／Enter／Escape |
| 既存機能 | 6館・温泉・港・道路・作品画面の配置は維持。通常画質と低設定で同じ経路。初期は通常画質・BGM ON | 既存の配置／経路テスト、ツアー、各館、温泉、セキュリティ検証 |
| URLと再開 | 通常表示、詳細クエリ、外部リンク、戻る／進むを維持。拡大率も現在位置と同じ保存データに記録 | ツアー全行程と中断、直接URL、再読み込み、旧保存位置のリセット |

`tests/`直下は単体テスト、`tests/browser/`はPlaywright CLIの`run-code --filename`で実行する実ブラウザ検証。画面・計測結果はローカルの`output/playwright/ux-*`に保存する。ブラウザ検証は`npm run build`後の`out`をlocalhost:3001で配信して行う。

## 再現した不具合

- 縦に45px上へドラッグすると、景色が45px下へ動いていた。ブラウザの射影座標でREDを確認し、修正後は指の移動と一致。
- 320px幅でカメラ操作と移動操作が重なった。矩形の重なり検査を追加し、修正後は解消。
- 読み込み中にWebGLを失うと代替案内が出なかった。中断検証をREDから追加し、生成の初期段階でも代替表示とリソース解放へ進むよう修正。
- 人物モデルの取得失敗時に入口カードが代替案内のリンクを覆っていた。エラー時は入口を退け、リンクを押せるよう修正。
- 全体表示で縮小すると近景へ切り替わる矛盾を修正。近景と全体表示の両方で同じズーム方向に統一。
- 画面が読めても音声操作と対応しないボタン名、自転車ボタンのコントラスト不足を検査で確認して修正。

## 負荷測定

Chromiumの390×844、DPR 3、CPU 4倍低速化、下り4Mbps、遅延150ms、BGM再生で測定。最適化前は最長2,278msのタスクで操作を塞いでいた。生成を分割した測定では最長421ms、通常表示のリンクは779msで利用可能、街の準備は4,958ms。街の準備全体を短くすることより、準備中も操作に応答することを優先した。

当初記録した5秒の徒歩移動中のrAF間隔は通常画質p95 23ms・最大30ms、低設定p95 22ms・最大30ms。ただしこれはブラウザのコールバック間隔であり、描画を間引く低設定の実際の3D描画FPSを示さない。検証用の時計も描画タイミングへ影響するため、FPSの根拠には使わない。実描画の比較には`tests/browser/world-frame-rate.js`を使い、日付だけを固定してネイティブのrAFと`performance.now()`を維持する。実機スマートフォン・Safari・実際の利用者による操作評価は未実施。

## 検証結果

- `npm test`：93件成功。カメラの射影と枠、歩行速度・アニメーション、全館・温泉・港の経路、既存の物理・画質・音声処理を含む。
- `npm run typecheck`、`npm run build`、`git diff --check`：成功。
- `world-ux.js`：5画面サイズで、ドラッグ・ピンチ・ホイール・ボタン・キーボード・拡大率の再開・全体表示・途中停止・操作の重なりを確認。
- `world-halls.js`、`hall-navigation.js`：4館ツアー、6館の入退館、自転車からの入館、外部リンク、前後移動・中断・履歴・直接URL・再開・低設定・Reduced Motionを確認。
- `project-exhibits.js`、`onsen.js`：拡大した実画面看板の表示とクリック、低設定での同一形状、温泉への移動と屋根の開閉を確認。
- `world-ux-loading.js`：準備中の閲覧、準備中に選んだ画質の保持、初期生成中のWebGL喪失と部分モデルの解放、モデル取得失敗から通常表示への移動を確認。
- `security.js`：全10ページのCSP、正規のスクリプト・WASM・BGM・画質切り替え、初期値、直接URL、外部スクリプト・通信・埋め込みの拒否を確認。
- axe：4画面サイズ×入口・探索・地図・館内・通常表示の20状態で、対象WCAGルールの検出0件。QA専用ブラウザで検査スクリプトを注入し、製品のCSPは変更していない。Lighthouseの入口と通常表示もアクセシビリティ100。自動検査は実利用者や支援技術での評価の代替ではない。
